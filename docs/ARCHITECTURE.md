# Voice architecture (local-first)

```
Browser mic (MediaRecorder) -> React VoicePanel
  POST /api/voice/stt   (audio upload: type + magic-byte + size checks, temp file deleted in finally)
      -> faster-whisper (local, one cached model instance, runs in a worker thread, timeout)
  POST /api/voice/chat  (text)
      -> agent.handle_turn -> Ollama /api/chat with role-filtered tool schemas
      -> tools.execute: role check -> pydantic validation -> (confirmation) -> RecruitmentRepo -> PostgreSQL / email / scheduler / GitHub
      -> audit log
  POST /api/voice/tts   (reply text) -> Piper (local) -> WAV -> browser <audio>
```
Each step is a separate request so the UI shows real progress (transcribing, thinking, speaking) and every stage has its own fallback: STT fails -> type; TTS fails -> text reply; Ollama down -> clear error (optional labelled keyword demo).

## Components
| Concern | Module | Swap by |
|---|---|---|
| LLM / STT / TTS | `services/base.py` interfaces, `services/registry.py` | add class + registry entry + env var |
| Tools, permissions, confirmation, audit | `tools.py` | add `Tool(...)` to `TOOLS` |
| Data access | `repo.py` (`RecruitmentRepo`) | implement on your SQLAlchemy models and services |
| Auth | `deps.py` | replace with your dependency (id, role, candidate id) |

## Security model
- The LLM can only name a registered tool. It never sees SQL, shell or free HTTP. Arguments are validated; unknown arguments are rejected.
- Candidate tools take identity only from the authenticated session; a `candidate_id` argument is rejected. Candidates are only shown candidate tool schemas, and roles are re-checked on every call and again at confirmation.
- Consequential tools (assign, schedule, invite, remind, advance stage, approve feedback, submit repo) only create a pending confirmation. The user confirms with yes/no (typed or transcribed from their own speech) or the buttons; the model cannot confirm. Wording of the confirmation prompt is generated by the backend so the model cannot claim the action is done. Confirmations are single-use, per-user, expire in 120 s.
- `OLLAMA_BASE_URL` must be loopback unless `OLLAMA_ALLOW_REMOTE=true`. Do not publish port 11434.
- Audio is deleted after transcription. Nothing is sent to cloud AI services. Conversation history is held in server memory (12 messages, 30 min) per user and stores only user/assistant text, not tool data.
- Prompt injection: tool data is labelled as data in the system prompt, but small local models can still be fooled. The real protection is the backend: authorization, validation, confirmation.

## Limits and known gaps
- Small local models can pick the wrong tool or arguments. Wrong or invalid calls come back as errors, and consequential ones still need confirmation. Always keep the on-screen tool lines visible so users can see which data was used.
- Confirmation store and history are in memory (single worker). Use Redis/DB for multiple workers.
- No rate limiting yet; add one on `/stt` and `/chat`.
- Push-to-talk (click to start/stop), not hands-free voice activity detection.
